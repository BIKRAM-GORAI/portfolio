ATTACKING MY OWN SYSTEM

“If I were trying to abuse this endpoint, what would I try?”

Functional testing only proves the happy path. Thinking like an adversary uncovered real production vulnerabilities:

01 CONCURRENCY & RACE CONDITIONS

Two simultaneous taps shouldn't double-spend.

A points balance was read in memory, validated, and then decremented. Under concurrent async requests, two incoming packets read the same original balance simultaneously—both passed, double-spending points.

Fix wasn't frontend throttling. It was making the database query itself an atomic state transition.

ATOMIC TRANSITION
find() then save()
Double-spend risk $inc with $gte
Zero underflow
02 CRYPTOGRAPHY & TIMING ATTACKS

Secrets shouldn't leak through nanoseconds.

Standard JavaScript string equality (===) short-circuits on the very first mismatched byte. An attacker measuring response times over thousands of attempts can leak secret characters byte-by-byte.

Replaced with hash normalization + constant-time byte-level comparison.

CONSTANT-TIME VERIFY
token === secret (early return leaks byte timing) crypto.timingSafeEqual(sha256(A), sha256(B))
03 SCALING & RESILIENCE

N+1 query cascades & unbounded memory.

Checking habit streaks in an iterative loop meant N users = N+1 DB queries. Meanwhile, an uncapped in-memory map leaked heap space over time. Both worked fine in local dev, but would choke under sustained production traffic.

Batched $in aggregation pipeline (N users ➔ 1 query) + LRU cache with strict 15m TTL.

BATCHED & BOUNDED
N users ➔ N+1 database network roundtrips Batched $in query: N users ➔ 1 single roundtrip
+ LRU cache cap (1,000 max) to prevent heap exhaustion
